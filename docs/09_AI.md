# 09 — AI Platform

## Providers

An injectable, tenant-neutral generator speaks to any **OpenAI-compatible**
base URL. Each tenant may supply their **own API key** (`organization_ai_settings`);
without one, the platform's included AI is used. A `DisconnectedWebsiteGenerator`
fallback keeps the app functional with no key.

## AI workspace (shipped)

The tenant **AI** section is an accessible internal workspace with five deep-
linkable sub-sections (`#ai/<sub>`): **Command Center** (default), **AI
Employees**, **Actions & Approvals**, **Knowledge Base**, and **Usage &
Settings**. See `08_MODULES.md` for the UI structure and `04_SECURITY.md` for
the approval + key-handling guarantees.

### Command Center

A conversational workspace: pick an AI Employee, chat, and read live data to
answer. Conversations and messages are **persisted** (`ai_conversations` /
`ai_conversation_messages`, see `02_DATABASE.md`) and are **private to their
creator** and tenant-scoped. The composer guards against duplicate submission,
announces status to screen readers, and preserves typed text after a recoverable
failure. Only the assistant's final text is stored — never chain-of-thought.

## Tool registry (shipped)

A closed, code-defined registry (`src/platform/ai/tools/`) exposes read tools
(run immediately) and write tools (**recorded as a pending proposal requiring
explicit human approval**). `buildDefaultAiTools` wires the honest starter set
from whatever services are available — e.g. `crm.leads.list`,
`crm.pipeline.summary`, `metrics.summary`, `clients.list`, `projects.list`,
`revenue.summary`, `tickets.list` (read) and `crm.leads.create`,
`crm.leads.update_stage`, `notes.add`, `notifications.send`, `projects.create`,
`tickets.create` (write). Each tool declares a role allowlist; every invocation
enforces role + `TenantContext`, and the AI never generates or executes raw SQL.
Approval security (single-use, expiry, role re-auth, payload binding, tenant
binding) is detailed in `04_SECURITY.md`.

## AI Employees (shipped)

Saved, tenant-scoped assistants with a name, job title, persona/instructions,
and a **whitelisted subset** of registry tools. The management UI creates/edits
them in a focused dialog with a **registry-driven tool picker** (searchable,
grouped, read vs. writes-needs-approval), and tool names are validated server-
side against the real registry. An employee can only ever do **less** than the
acting user's role allows — the Command Center intersects the employee's tool
list with the role-permitted set, so a persona can never elevate privilege.
Employees can be paused (archived) or deleted. Generated/automated activity is
always labeled as such; high-risk actions stay approval-based.

## Knowledge Base

Collections → documents → chunks. v1 retrieval is keyword-based over Postgres
behind a `RetrievalProvider` interface; answers are **grounded** strictly in
retrieved chunks and cite their source documents, returning empty when nothing
matches. Embedding + pgvector retrieval and LLM answer synthesis are planned.
See `08_MODULES.md` (Knowledge Base) and `04_SECURITY.md` (AI safety).

## Embeddings

Not yet generated (v1 is keyword). The interface is embedding-agnostic; a
`PgVectorRetrievalProvider` will embed documents at ingest and queries at ask
time.

## Usage metering

Every AI generation records a usage event (`ai_usage_events`) in micro-dollars;
monthly **plan allowance caps** gate platform-key usage. BYO-key usage runs on
the tenant's own account.

## Safety

- Ground answers in retrieved material; never fabricate.
- Preview + explicit confirmation before any write; per-tool permission +
  tenant enforcement; full audit of request → proposed action → confirmation →
  execution → result; never expose secrets (see `04_SECURITY.md`).

## Future AI roadmap

pgvector semantic retrieval; document ingestion beyond text (PDF/Docx/URL) with
inline-cited answer synthesis; provider-key encryption at rest (pending a KMS
decision); durable request idempotency for the Command Center; conversation
sharing options beyond creator-private.
